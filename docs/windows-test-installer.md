# Windows 测试安装包 1.1.0-test.8

本次更新：

- 修正中等延迟被反复丢弃的问题：保留最多 200 ms 的发送时钟延迟并逐步追回，完整帧之间仍至少间隔 10 ms。正常目标保持每包 20 ms 音频、每秒 50 包；不会永久加倍发送，也不会在一次回调中突发发送多包。
- 超过 200 ms 的延迟、实际积压等待、暂停恢复和发声方切换重新计时；不追赶暂停或拥堵期间的时间。继续保留 64 KiB 暂停、16 KiB 恢复、1 MiB 硬上限及 15 秒超时，停止和发送失败立即取消后续帧。
- 增加运行期间累计发送时长、音频时长、追赶与重新计时统计；每次已有诊断汇总都保存累计值，旧日志滚动清理后仍能分析长时间发送不足。不增加逐包磁盘写入，不记录音频内容。
- 本次恢复积压优化前的有限追赶范围，同时保留后续发送间隔和积压保护。代码回归及纯计时计算不能证明机器人运行 2–3 小时后的音质已解决；接收端缓冲及实际发声仍没有回传确认。

继续包含 test.7 的更新（其中整帧迟到的处理由上述规则替代）：

- 修正持续发送偏慢：将 20 ms 音频时钟与最小发包间隔分开，避免迟到逐帧累积。Windows 定时器取整是迟到的一种可能来源，客户日志未证明具体操作系统原因。同一连续会话内，完整帧可在不小于 10 ms 的间隔内校正普通迟到；迟到达到一整帧后重置时钟，不在一次回调中突发补发。
- 暂停恢复、音频交接和最后一帧保留完整的实际音频时长；未到发送时刻或仍有本地积压时不取下一帧。目标仍是每 20 ms 发送 20 ms 音频，不承诺操作系统定时器完全无抖动。
- 音频诊断增加最近连续帧的发送速度、累计延后和采样时间。按同一会话及连接统计，排除已记录的暂停和切换；历史最大间隔不再被当作当前发送状态。
- 完成记录增加音量处理后的 PCM 峰值、均方根及非零样本数，用于区分应用输出静音和有信号。记录不保存音频；有信号、发送成功均不等于机器人已经收到或发出声音。
- 长音频播放过程中每秒汇总发送信号强度，不必等整段结束；暂停、会话与连接切换分开统计，写入回调不重复计数。
- 大音频哈希每处理 1 MiB 让出事件循环，减少准备下一段时对发送及停止操作的连续阻塞；缓存空间充足时跳过重复的 LRU 扫描、排序。
- 强化可复用句子来源的任务清理：取消已弃用的合成请求，忽略迟到回调，释放监听器及缓存引用。
- Windows 交付增加实际计时器测量：用生产调度函数发送 500 次计时样本，测量 10 秒音频对应的发送节奏；总延后超过 10%、突破最小帧间隔或缩短尾帧时阻止交付。此检查不连接机器人、不模拟接收端、不调用语音服务。

继续包含 test.6 的更新：

- 音频发送增加缓冲等待：积压达到 64 KiB 暂停取下一帧，下降至 16 KiB 后继续；硬上限从 256 KiB 调整为 1 MiB。等待期间不丢帧、不推进序号。
- 连续等待 15 秒仍无法恢复，或达到硬上限时，立即阻止旧连接继续接收音频和控制指令，再终止旧连接、释放本地未发送数据。客户端模式 5 秒后重连；服务端模式等待机器人重连。恢复后需重新开始播放，不自动恢复移动或巡游。

## 安装前

- 测试版沿用相同应用标识，**会替换旧版本并使用同一份用户数据，不是独立沙盒**。
- 先停止现场任务、退出应用，再备份 `%APPDATA%\robot-live-ui\`。安装器不会清空用户数据，但应用正常使用仍会更新配置和日志。
- 保留旧版安装包。需回退时先退出测试版，安装旧版，并按需要恢复备份；不要在运行中覆盖数据。
- OCR 需要 Microsoft Visual C++ v14 x64 Redistributable。本测试版已随安装器附带运行库，离线安装时也会运行；可能需要批准管理员权限或按安装器提示重启。参见 [ONNX Runtime 的 Windows 要求](https://onnxruntime.ai/docs/install/#requirements)。GitHub 托管运行器通过不等于未配置的 Windows 电脑已经通过。
- 首次安装是空巡游、空知识库、关闭且为空的过渡音频。需自行配置机器人地址、语音凭据和内容。升级不会以这些默认值覆盖已有文件。

## 构建与交付约束

1. 在独立的 `codex/` 分支提交已审查代码，完成本地回归，排除个人设置、录音、日志、缓存和密钥；PR 检查全部通过后才打标签。最终交付仍须通过精确标签提交的完整 Windows 检查；其他提交的绿色结果不能替代。
2. 测试标签必须与 `robot-ui/package.json` 的版本完全一致，格式为 `v<主版本>.<次版本>.<修订号>-test.<序号>`，并指向已审查的精确提交。已存在的标签/发布不得移动、覆盖或复用；新的修复须使用未用过的测试版本。
3. 标签触发 Windows 构建。PR 任务只有读取权限；只有测试标签/精确标签手动任务获得草稿交付权限。普通 `main`、PR 或正式版本标签不会创建测试发布。
4. 交付前运行后端/UI 回归、实际资源允许清单与隐私检查、打包 Electron 的实际音频计时及 FFmpeg/Sharp/ONNX 测试，以及窗口与后端连接、端口占用兜底检查。还须通过真实 NSIS 安装/覆盖升级与三机器验收，并再次用安装目录中的 Electron 通过运行检查。
5. 创建新的 **draft + prerelease**，附安装包、`SHA256SUMS.txt`、`build-info.json`、`packaged-runtime.json`。脚本校验事件、标签、版本、本地提交和远端标签提交，不使用 `--clobber`。已经存在的草稿或公开发布均拒绝覆盖。
6. 下载交付资产并核对 SHA-256 后提供测试。Actions 附件上传是辅助渠道，即使其配额不足，草稿交付也必须单独成功；绿色检查本身不是可下载安装包的证明。

草稿只对拥有相应仓库权限的人员可见；标签和提交仍遵循仓库本身的可见性。本流程不合并 `main`、不更改签名配置。已获授权的客户公开下载单独交付经过校验的安装器与最小校验文件，不公开源码仓库或内部构建溯源资料。

如需给已验证的草稿补充 `streaming_app.zip`，可在 Build and Release 工作流中选择包含归档脚本的分支，
填写原测试标签并开启 `archive_only`。此任务只在 GitHub 运行器内下载和封装：校验标签提交、
成功的原构建、所有资产 SHA-256 和该版本必需的运行检查，再上传 ZIP 及其校验文件。新增发送节奏检查后，
归档验证器的必需清单也必须包含 `audio-send-cadence`，不能沿用旧版九项清单放行新构建。ZIP 只放一个安装器、
原构建报告和说明，不重复放入安装器内部依赖；已有同名 ZIP 会拒绝覆盖。原应用标签和安装器保持不变。

| 原地播报 | 使用巡游讲解配置；单次、整段循环及停止正常；切页/分屏继续，重启不续播；不移动机器人 |
| 升级与缓存 | 不清空用户数据即可播报；旧占用记录不阻塞；保存设置时最多一个后台；机器 1/3 播放期间重启 2 不受影响 |
| 机器人 MP3 | 使用与 Python 客户端相同的文件和连接，对比连续性、音质、停止响应；不要同时运行两个发送端 |
| 机器人 TTS | 长文逐句自然衔接、克隆音色一致；准备中的高优先级音频不抢断，准备好后按当前句尾交接 |

| 诊断 | 正常、断连、后台退出后均能从界面导出已保存的音频及机器人记录；连接失败与目标确认失败可区分，默认不含原始后台输出；不要求打开后台控制台 |

相机和推流设置未改变。同一相机/手机麦克风采集机器人扬声器时，准备延后的是开口时间，不是另一路音轨偏移；仍须检查最终录制的场景、句尾和画面同步。

机器人没有可听完成确认，因此句尾仍是发送端估计。若有明显卡顿、吞句尾、跳过后继续旧讲解或不可接受的停播延迟，保留诊断与录制，不转正式发布，不通过猜测延时掩盖问题。

例如，640 字节代表 20 ms 音频；若长期每 31 ms 才发一帧，应用发送速度只有约 `0.65×`，10 秒音频约需 15.5 秒发出。这是持续发送偏慢，不只是某一次抖动；接收端已有缓冲耗尽后可能断续。单次最大间隔、缓冲为零或写入回调正常，都不能单独证明当前音质正常。实际机器人缓冲深度和扬声器状态没有回传确认。

## 原地播报改写与依赖验收（test.4）

原地播报使用巡游讲解的 LLM，独立保存默认/自定义提示词和可空的补充风格要求；自定义模式下补充风格置灰且不发送给模型。循环时提前一轮改写，播放和预改写同时取消，原文/改写稿切换仅用于查看。

安装验收在真实 NSIS 覆盖安装后，再用安装目录中的 Electron 执行完整原生运行检查：ONNX DLL、Sharp、两套 OCR 模型与字典、OCR 推理、FFmpeg/FFplay、Windows 暂停模块。任一失败均阻止测试版本交付。Windows 包为 x64，目标客户系统为 Windows 10/11；CI Windows runner 的通过记录不等同于每个客户硬件上的现场验收。

当前运行报告共十项必需检查，含新增 `audio-send-cadence`。该项直接测量实际 Electron 计时器，报告平均/p95/p99/最大帧间隔、累计偏移、迟到次数和 CPU 使用量；不对每次唤醒或 CPU 百分比设置零容差。运行源码的本地预检无法代替 Windows 打包及安装后的检查，软件测量也不证明机器人现场发声效果。

现有三机器安装验收还会利用已采集的实际后台回环 PCM，对完整连续片段检查整体接收速度：首帧到末帧的接收间隔与其前面各帧的音频时长比较，持续延后超过 10% 时失败。主动重启或崩溃截断的片段不参与此速度门槛；它们仍检查内容与序号。回环回调可能合并到达，因此不对单个接收间隔设最小值，也不将此工程门槛视为机器人缓冲耗尽或现场音质的判据。
